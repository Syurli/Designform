# 策问项目文件格式 v1

这是提供给用户和任意 LLM 的独立读写约定。无需阅读策问源码。

## 入口与目录

项目根目录的 `PROJECT.md` 保存短 YAML 头部：`id`（稳定项目身份）、`name`、`format: 1`、可选 `description`、`example`。

当前稿在 `docs/`：`gdd/` 放总纲，`dd/` 放专项设计，`questions/` 放独立问题，`assets/` 放相对路径附件。只把当前任务需要的文件交给模型；历史按需读取。

文档使用 UTF-8。换行和未修改的文本保留原样。文件名可中文，文档 ID 和锚点使用字母、数字、短横线和下划线，项目内唯一。

## 文档身份与归属

GDD、DD 与问题文档使用简短 YAML 头部：

```yaml
id: dd-resources
type: dd
status: draft
system: system-resources
```

`type` 为 `gdd`、`dd`、`question`；普通说明文件不需要进入图谱。`status` 为 `draft`（草稿）、`question`（待确认）、`confirmed`（已确认）、`archived`（已归档）。问题文档也可用 `open` / `answered` / `partially-decided` / `decided` 表示问询进度，图谱仅把尚未落实的问题标为待确认，不把答案自动变成正式规则。

GDD 的头部可声明 `systems` 列表，每项包含稳定 `id`、`title`、可选十六进制 `color`。DD 的 `system` 指定主要归属；普通工作分组保存在编辑器工作区，不写入此字段。

普通段落不必拥有 ID。需要引用的规则使用锚点和标题：

```markdown
<a id="rest-cost"></a>

## 休息成本

这里写规则正文及仍待决定的边界。
```

该规则的完整身份是 `dd-resources/rest-cost`。改标题、移动段落时保留 ID；复制为新规则时使用新 ID。

## 阅读优先与正式关系

策划正文先写玩家体验、规则、理由和例子。首段简述这份设计负责什么；可选 `summary` 头部字段用于悬停预览。普通阅读不要求读者理解内部 ID 或功能字段。

把联系融入自然语句，例如 `玩家沿着[地图结构](dd/DD-001_地图结构.md)规划路线`。GDD/DD 中使用相对于自身位置的真实 Markdown 链接，具体规则追加 `#锚点`。显式正文链接直接形成引用关系，无需重复添加关联表。软件还会为正文中名称唯一的其他文档提供同名词阅读提示，但这种提示本身不新增正式关系。

仅在需要表达依赖、约束等额外语义时，在文末使用关联索引：

```markdown
### 关联索引
| 关系 ID | 来源身份 | 类型 | 目标身份 | 依据 |
|---|---|---|---|---|
| rest-time | dd-resources/rest-cost | 依赖 | dd-time/time-step | 休息需要明确耗时。 |
```

类型支持依赖、约束、关联、引用、替代。目标身份负责跨重命名定位，普通相对链接负责阅读；文档级目标只写文档 ID。反向联系由工具派生，不复制第二份关系。包含关系来自文档结构，不在这里手工制造循环。

来源身份必须属于本文件，文档级来源只写文档 ID，规则级来源包含锚点。既有的规则下关系表仍可读取；无需迁移已有项目。阅读器将识别到的功能表统一后置并折叠，普通设计表格仍原位展示。具体写法可参考随软件提供的 `cewen-collaborate/references/WRITING.md`。

星图以有效的 GDD 为中心。通常一个游戏保留一份主总纲；存在多份时优先 `GDD.md`，其次按路径稳定选择，已归档总纲不作为中心。无总纲时不凭空生成设计内容。

## 独立问题

一个可追踪问题一份 Markdown，多个 DD 引用同一问题。在问题内分开保存背景、可选方案、用户原始回答、模型解释、决定记录、文档落实。推荐选项不代表用户作答；改答追加记录，不润色历史原话。

最终采纳的规则写回相关 DD；问题文档保存依据和各 DD 的落实状态。编辑器私人笔记与阅读批注默认不公开，发布为问题后才进入文档。

## 历史与提交

`versions/V000001/docs/` 是当时的完整快照；每版有可读说明和校验清单。`versions/BASELINES.md` 保存命名基线；`INDEX.md` 是导航。不要直接修改旧快照。恢复旧稿会创建新版本。

每轮需要精确保留时显式提交并确认成功；文件监听只能捕获实际观察到的稳定状态。`.cewen/` 是编辑器工作区，模型无需读取或修改。只有索引可以重建，私人笔记、未提交草稿和恢复日志仍需备份。

## 编辑后的检查

保留身份，核对相对链接，不改历史目录；报告修改文件、设计理由和未决问题。涉及多文件时以明确批次提交，或在全部落盘后告知完成；不要把中间文件状态声称为整批已完成。

## 问询字段与批次

问题头部可包含 `round`、`baseRevision`、`targets`、`mode: single` 或 `multiple`。`follows` 指向前题；`when: {questionId, option}` 要求前题已回答且选项原文匹配，未满足时保留题目但暂不能作答。背景放在“问题背景”，选项以 `- A：`、`- B：` 开始。每次改答追加“回答 ID、时间、基础修订、选择及当时原文、用户自定义原话”，不覆盖旧答案。

模型提案包含 `id/title/reason/baseRevision/questionIds/dependencies/changes`。每项 change 是 `path/baseHash/text`；dependencies 至少记录所引用问题的文件哈希。来源问题候选保留用户原话，另写模型解释与决定；用户采纳时工具维护逐 DD 落实表。

多文件外部协作先使用 CLI/MCP `begin-batch`，全部落盘后 `end-batch`，以一轮说明发布版本；普通编辑器单文件修改可由监听观察后发布。没有运行中的服务时，后续打开只能记录最终存在的文件，不会伪造中间版本。

工作草稿保存在 `.cewen/drafts`，服务断开时浏览器另保留应急副本。草稿不等于正式文档，也不属于公开版本。不要将 `.cewen` 全部交给模型；需要共享批注时由用户显式发布或选择。
