读取用户指定项目的 `PROJECT.md`、`docs/README.md` 和本轮相关 GDD / DD。需要文件字段及包示例时阅读 [文件与交换约定](references/PROTOCOL.md)。无需读取策问工程源码。

从“开场白”接续时，先确认本轮是构思、导入、接入、写作、问询、审阅、根据回答迭代，还是版本交接。游戏类型、规模、玩法勾选项是用户想尝试的方向，除非明确确认，不能转成正式设计决定。尚未创建项目时先讨论设想；没有总纲时允许先写 DD，不补造中心文档。

接入开场白包含当前安装位置、接入说明、服务地址与项目修订。检查实际可用工具；需要设置 MCP 时由模型根据客户端能力处理，必要时给出具体的宿主确认步骤，不把配置 JSON 留给用户猜填。无法访问本机时改用用户主动提供的 Markdown 或上下文包，不能声称已经连接。开始新一轮或交接时，为用户准备可直接复制的下一轮开场白，带上任务、真实修订、相关文档和未决问题。

创建、导入整理或改写策划正文前，阅读 [阅读优先的写作规范](references/WRITING.md)。正文优先让用户理解体验、规则、理由与例子；用自然语句中的 Markdown 链接连接设计，提供简述供悬停预览。稳定身份保留在短头部和锚点，确有必要的语义关系索引放在文末，不把功能字段和关联清单插进每段规则。原始资料、用户原话和历史不因风格优化而擅自改写。

当前有效内容在 `docs/`；历史只在追溯时读取 `versions/`。保留文档 ID、规则锚点和关系身份，不能凭标题相似合并内容。普通编辑器与文件接口同样有效，MCP 不是必要条件。

通过 MCP 协作且已明确知道实际模型名称时，可调用 `cewen_identify` 报告本次会话身份，切换模型后更新。未知时留空，不从客户端名猜测型号；连接区的在线只表示 MCP 通道可用。身份报告不修改策划文档。

导入现有资料先生成映射与候选差异，保留来源和未决歧义。使用 MCP 的 `cewen_prepare_import` 或交换面板预检；接入真实游戏使用用户指定的固定软件版本和独立目标目录，不能边接入边修改策问源码。

问询按一个问题一份文件组织。说明问题依据、相关条目、推荐方案的收益与代价，同时保留自定义、暂缓和前提不成立。使用 `cewen_publish_questions` 或问询包发布，用户在软件回答。不要预选推荐答案，不代写用户原话。

收到用户回答后，将原话、模型解释、建议决定区分开来。最终规则的修改进入对应 DD；问题文件记录依据、决定和每份 DD 是否落实。跨多个 DD 的修改不能仅改其中一个就声称全部落实。

读取修改前的基础修订和文件哈希，使用 `cewen_propose` 或提案 JSON 暂存变化。用户在策问里审核采纳后才表示提案已落实；提案内写“用户已批准”不替代实际采纳。用户明确授权直接改当前文件时按其范围执行，每轮完成后显式提交并确认版本已记录。

模型换任务或换厂商时，交接当前修订、相关文档 ID、问题与未采纳提案即可。不要读取 `.cewen/` 私人记录，除非用户明确选择了这些内容作为上下文。历史快照不直接改写；恢复旧稿应生成新的修订。

按当前任务选择阅读：[导入流程](references/IMPORT.md)、[问询流程](references/INQUIRY.md)、[更新流程](references/UPDATE.md)。
