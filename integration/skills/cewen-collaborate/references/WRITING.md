# 阅读优先的策划写作

适用于在策问中编写 GDD、DD，以及经用户授权整理已有策划。先满足读者理解设计，再满足工具索引。用户另有明确格式时遵循用户要求。

## 从游戏设计开始

标题之后先用一两句说明这份设计负责什么、玩家能感受到什么。可用短的 `summary` 头部字段补充预览摘要，否则策问取正文首段。不要把 ID、文件位置、依赖枚举写成开篇。正文按设计需要组织目标、操作、反馈、约束、例子和待决定边界，不必凑齐固定章节。

一段规则尽量在一个地方完整定义。其他 DD 在解释本地行为时引用它，不复制出多份可能冲突的规则。已确认、建议和未决定保持清楚；排版调整不创造用户未决定的玩法。

## 把联系写进句子

例如控制系统 DD 的正文：

```markdown
# 控制系统

玩家通过少量固定操作完成移动、瞄准和装备切换。

按下切换键时，[武器系统](DD-武器系统.md)选择下一件可用装备；
没有其他可用装备时保持当前选择，并给出轻量提示。

长按行为沿用[武器系统](DD-武器系统.md)的切换约束，
控制系统不重复定义装备冷却。
```

示例文件名仅示意；实际链接必须指向已存在或本批次同时创建的目标。引用具体规则时使用 `相对路径.md#稳定锚点`，链接文字使用自然的文档名或词语，不显示内部身份。文档跨目录时计算真实相对路径。

策问会为明确链接显示下划线和悬停摘要；当前项目中名称唯一的其他 GDD/DD，重复出现在普通段落时也有阅读提示。可移植的正式引用仍应写成 Markdown 链接，让普通编辑器和其他模型同样能理解。仅自动提示的名称不构成正式知识边。名称含糊、有同名目标时显式选定链接，不凭相似度猜测。

摘要说明设计责任或关键规则即可，不罗列元数据。一般 40～100 个汉字足够；短文可以更短。代码、示例字符串、标题不为了凑链接而强行标注。

## 功能信息后置

自然引用不要求另写一份“本 DD 关联如下 DD”；正文链接已经能建立引用关系。只有依赖、约束、替代等需要表达额外语义时，才在文末保留简洁的关联索引：

```markdown
### 关联索引

| 关系 ID | 来源身份 | 类型 | 目标身份 | 依据 |
|---|---|---|---|---|
| control-switch-limit | dd-controls/switch | 约束 | dd-weapons/cooldown | 切换遵循装备冷却，不由输入层绕过。 |
```

来源必须属于当前文档；保留既有关系 ID。文档级来源仅写文档 ID，规则级来源加锚点。工具在阅读页将该表收在文末，按需展开。不要把整篇正文包进 HTML 折叠块，普通 Markdown 应能独立阅读。

GDD 是游戏方向和整体设计的入口，通过正文概览主要系统；DD 展开细节。独立问题文档保存讨论过程，已采纳规则回写 DD；不要把长篇问答记录塞入设计正文。

## 交付前核对

连续阅读正文，确认不依赖 ID 清单也能理解设计；链接目标和锚点存在；文首有可用简述；规则与未决问题分明；必要功能索引在后面；稳定身份未损坏。导入整理应展示候选差异，不自动迁移用户的已有项目或改写历史。
