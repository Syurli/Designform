## 1. 本次确定的边界

### 1.1 用户已经确认的要求

1. 现有视觉与动效暂时封板，作为后续开发的基线。
2. 主总览只保留星图 3D 与系统分层；关系分析是选中内容后进入的次级页面。保留传统策划案、卡片阅读方式；不恢复关系矩阵。
3. 用户必须能够不依赖 LLM，手工建立和维护项目。
4. 当前游戏衍生内容应改造成通用基础示例工程，不能当作真实游戏已接入。
5. 工具开发与真实游戏接入是两条独立工作流。首版工具完成后，由用户在战术巫师的策划对话中发起接入，作为实机验收。
6. 正式版需要实用的分组、注释、标记等整理能力，以及版本控制和 LLM 问询协作。
7. 每个项目有独立、干净的文档目录；GDD / DD 为 Markdown，用户和 LLM 可直接读写。编辑器数据与文档分离，读取策划无需阅读策问源码。
8. 各次文档修订必须有版本记录，版本历史纳入项目路径结构；通过既有 3D / 分层界面的版本切换、生长与变化展示查看演进。

版本管理及其图谱展示为 **P0 首版必达能力**。从第一次正式保存即保留项目快照；提供项目、文档、知识条目三个历史入口，共用一条修订链。版本时间轴管理修订先后，3D / 分层画布展示所选版本的策划关系；历史阅读、比较和恢复使用同一套公开快照。它们不能降级成只存编辑器数据库的操作日志，也不能只交付演示动画。

本文对功能细节、技术选型、优先级的安排属于建议方案。本文取代旧方案中“边开发工具边导入真实游戏”的阶段安排，以及与当前封板导航不一致的展示设想。旧报告保留历史身份，不继续作为实施范围的依据。

### 1.2 封板的具体含义

保留当前布局语言、星空风格、选中反馈、阅读层级和页面过渡；现有总览切换 1150 ms、分析进入与返回 520 ms、内部换焦点 360 ms 作为回归基线。后续新增项目中心、编辑器、版本与问询界面沿用这套视觉语言。

封板不阻止补充业务表单、空状态、保存反馈、可访问性与必要缺陷修复。新增版本时间轴和生长展示沿用现有视图，不改变主总览导航；性能优化也必须以保持已确认体验为条件。

### 1.3 当前真实状态

以下按当前仓库代码核对基础能力；存在实现不等于完整功能已通过验收。本次只更新方案与验收要求。

| 部分 | 当前情况 | 正式开发要补齐的内容 |
|---|---|---|
| 知识空间 | Vite、TypeScript、Three.js；已有动态文档数据接入基础 | 结构变化时的布局连续性与完整同步验收 |
| 示例数据 | 已有独立的虚构 Markdown 示例及生成脚本 | 示例完整验收、异常夹具与发行资料核查 |
| 文档与关系 | 已有 Markdown 解析、手工文档编辑及关系读取基础 | 便捷结构编辑、关系维护、归档恢复 |
| 项目与存储 | 已有项目目录、项目中心、文件保存和草稿基础 | 外部同步、冲突及恢复完整验收，备份与迁移 |
| 版本 | 已有公开快照、校验清单与版本列表基础 | 命名基线、历史阅读、比较、恢复和 3D / 分层生长展示 |
| LLM 协作 | 没有实际导入、问询、提案或 MCP | 与模型无关的协议及完整问答回写闭环 |
| 桌面软件 | 没有桌面壳 | Windows 安装或便携交付、本地浏览器访问 |

当前软件包中的版本号不表示上述正式能力已经交付。下文“首版 / V1”特指首个达到本文验收条件的版本。

## 2. 产品应完成的五个闭环

1. **手工创作：**新建项目 → 写 GDD / DD → 提取知识条目 → 建立关系 → 保存 → 重开继续。
2. **整理阅读：**搜索 → 组织工作分组 → 做批注和标记 → 从不同视图定位同一内容 → 完成复核。
3. **设计迭代：**保存修改 → 对比版本 → 为里程碑命名 → 追踪为什么修改 → 必要时恢复。
4. **LLM 协作：**读取限定范围 → 提出问询 → 用户回答 → 形成修改提案 → 用户采纳 → 生成新修订。
5. **项目接入：**选择来源 → 预检和映射 → 审核候选内容 → 可恢复批次导入 → 核对来源与数量 → 可重复接入或恢复。

这些闭环共用同一份 Markdown 内容和公开格式；编辑器与受控接口共用提交服务，外部直接改文件则由同步与冲突机制接入。LLM 是参与者，不能成为打开、编辑、导出项目的前置条件。

## 3. 项目中心与手工创作

### 3.1 启动与新建

项目中心提供：最近项目、新建空白项目、从基础模板新建、打开已有项目、导入项目包、体验示例。

- 新建必填项只有项目名称；描述、图标等可后补。
- “空白项目”不产生任何设计结论，允许真正从空项目开始。
- “基础 GDD”创建可删除的栏目提示，例如目标体验、核心循环、系统列表、未决问题；提示不是既定规则。
- 示例是独立项目，支持“复制为我的项目”和“恢复示例”；重置不能影响用户项目。
- 用户能够重命名、复制、归档、打开项目位置、备份和移除最近记录。移除记录不删除数据。
- 真正删除项目单独操作，清楚显示目标项目和备份状态；不能与关闭项目混淆。
- 首版无账号要求。个人偏好采用本机配置；“个人”不代表已经具备多用户隔离或云端权限系统。

### 3.2 编写体验

提供 GDD、DD、章节、可引用条目的新建与编辑。首版采用有中文格式工具栏的 Markdown 编辑器与预览，不要求用户熟悉语法。支持标题、列表、表格、引用、链接和本地图片附件。

普通段落不必全部变成图谱节点。用户可以把需要讨论、复用、追踪的段落“设为知识条目”，也可以先建立条目再编写正文。GDD 可引用各 DD 的条目，DD 可引用其他 DD 的条目。

**正文只有一份，保存在项目 Markdown 文件中。** 编辑器把 Markdown 解析成有序内容块，图谱节点和卡片指向对应段落；被引用的内容不会复制出第二份可独立编辑的正文。只读摘要可以派生或单独说明，但不能悄悄覆盖原文。保存局部修改时保留其他原始文本，不重排整份文件。

文档编号只是显示字段，例如 DD-01；真正身份由稳定 ID 决定。重命名、移动章节、调整编号后，关系、评论和历史链接仍然有效。复制为独立内容时生成新 ID，并保留“复制自”的记录。

### 3.3 创建和维护关系

通过“添加关系”选择目标、关系类型和说明，保存前以自然语言展示方向，例如“资源恢复规则依赖时间推进规则”。

首版支持：引用、依赖、约束、关联、替代。系统归属与章节包含使用单独的结构字段，不混入普通关系编辑。主归属形成树，禁止结构循环；普通关系允许形成知识网络，不把所有环都视为错误。

关系也有稳定 ID、说明、来源和创建者。方向错误可反转；重复关系给出提示。拖动节点只是调整查看位置，不会隐式创建或修改策划关系。

归档内容前显示被引用的影响。被归档目标保留可追溯入口，不让已有关系成为无法解释的悬空线。永久清理需要处理引用，首版不提供批量无提示硬删除。

### 3.4 保存与恢复

- 输入自动保存为可恢复草稿，显示“保存中 / 草稿已保存 / 已保存为修订 / 保存失败”。
- 用户点击保存或快捷键后，把连贯修改提交为内容修订；不把每次按键都变成版本。
- 切换项目或关闭窗口前，说明尚未提交的草稿，允许提交、保留草稿或明确放弃。
- 正文撤销重做、实体归档恢复与历史版本恢复分开，不用一个“撤销”按钮承担所有语义。
- 保存失败保留草稿；重开可恢复。受控上下文导出默认使用已提交修订，编辑器草稿只有用户明确选入时才可见。外部直接读取 `docs/` 则以磁盘当前稿为准，批量修改期间可能看到尚未完成的状态，应等待完成信号。

## 4. 分组、批注和标记

以下核心能力纳入首版，不能全部后置为“以后做”。

### 4.1 四种组织方式分别负责什么

| 能力 | 示例 | 是否改变正式策划结构 | 首版范围 |
|---|---|---|---|
| 系统归属 | 资源系统、时间系统 | 是 | 自定义系统、排序、颜色和主要归属 |
| 工作分组 | 本周讨论、需要美术一起看 | 否 | 手工分组、嵌套一层、排序、多组收纳 |
| 标签 | 新手引导、数值、跨系统 | 否，属于编辑器整理信息 | 项目标签、重命名合并、批量设置 |
| 保存筛选 | 所有待确认且带“数值”的条目 | 否 | 保存搜索条件和视图入口 |

同一条目可属于多个工作分组，正文仍然只有一份。删除工作分组只删除集合，不删除内容。系统归属用于分层视图；工作分组用于限定关注范围，不能移动一次分组就改变游戏系统结构。

工作分组默认个人使用，可明确设为项目集合。首版使用本地配置区分作用范围，不承诺多人共享服务。复杂的自动分组规则引擎放在后续；保存筛选已经满足常见动态集合需求。

### 4.2 注释的两种形式

**个人笔记：**用于阅读记录、灵感和临时提醒，默认不进入策划正文、阅读导出或 LLM 上下文。

**项目批注：**可附着于文档、条目或正文片段，有回复、已处理、重新打开状态。首版支持本地用户及 LLM 提案所带的批注，不以多人在线为前提。

片段批注保存内容块 ID、写下时的修订、原文摘录及定位信息。正文改变导致定位不可靠时，展示“原位置已变化”和旧摘录，允许重新定位，不能默默贴到另一句话上。

批注与私人笔记保存在编辑器工作区，不直接塞进 DD。批注可明确转换为独立 Markdown 问题或正文修改草稿，转换后保留来源。点“已处理”只代表讨论已处理，不代表建议已经写入规则。需要让另一个 LLM 无软件续接的讨论，应显式发布到问题文档。

### 4.3 标记和状态

| 类型 | 建议内容 | 规则 |
|---|---|---|
| 个人标记 | 收藏、稍后阅读、待复核 | 不改变设计状态，不污染内容修订 |
| 项目关注项 | 风险、阻塞问题、需要外部依据；附原因和优先级 | 是待办式关注记录，不自动变成设计结论 |
| 设计状态 | 草稿、待确认、已确认、已废弃 | 只有明确确认才进入“已确认” |
| 来源状态 | 已记录来源、来源待核对、来源有冲突 | 来源存在不等于设计已确认 |
| 实现状态 | 首版可留空 | 不从设计状态推导“已实现 / 已测试” |

标记须有文字或图标，不能只靠颜色。风险优先级与设计完成度是不同字段。实现证据、游戏版本和试玩验证的完整管理放在后续，不把策问扩展成开发排期工具。

### 4.4 阅读效率

统一搜索标题、正文、编号和标签，提供按系统、对象类型、状态、来源、未决问题筛选。进入关系分析时，筛选不能隐藏解释当前焦点所必需的直接依据。

提供复制条目链接、定位到文档原位、最近浏览、回到上次位置、清除筛选、批量加标签和加入分组。批量归档先展示影响。快捷键有可见菜单替代，输入正文时不能抢占编辑按键。

保存视图记录模式、筛选、分组和镜头，与策划内容版本分开；历史版本中的镜头也不会反向修改当前正文。

## 5. 版本控制应面向策划人员

不要求用户使用 Git。首版采用线性修订历史和命名基线，暂不做分支合并。当前文档位于 `docs/`，各版本的完整文档快照、说明、校验清单和版本索引位于公开的 `versions/`，无须查询数据库也能读旧稿。具体目录见配套规范。

### 5.1 三类记录

1. **文档修订：**正文、结构、语义关系、设计状态及已发布问答文档的提交；可完整还原当时文档及图谱。纯问答变化也有版本，但不制造假的图谱变化。
2. **编辑器工作记录：**批注、私人笔记、未采纳提案、导入暂存等，保留修改与采纳记录，关联相关文档修订；正式问题、原始回答、解释和决定另有公开 Markdown。
3. **个人设置：**收藏、阅读位置、私人分组与笔记；单独保存，不制造策划内容版本。

一次受控提交可以更新多份文档和工作记录，但文件系统多文件写入不承诺天然原子性，必须有日志和恢复机制。纯阅读动作和编辑器批注不会使正在审核的正文提案无故失效；修改提案所依赖的答案则会让提案需要重新确认。

### 5.2 用户能看到什么

- 历史列表：时间、操作者、修改原因、改动数量、手工 / 导入 / LLM 来源。
- 命名基线：例如“首次评审版”，本质是给一个确定修订起名字。
- 语义比较：新增、删除、移动、正文差异、状态变化、关系变化；不要求阅读 JSON diff。
- 历史阅读：文档与图谱一致，明显标注只读历史状态。
- 恢复预览：展示将恢复什么、有何后续影响。确认后创建一个新修订，旧历史不会消失。
- 版本时间轴：在既有 3D / 分层中查看历史、比较两个版本、逐版播放演进。按稳定 ID 保持节点位置；新增节点与关系生长，修改高亮，删除收拢，移动平滑过渡。支持暂停、快速跳转及减少动态效果。

文档快照与版本轴共用同一修订来源，不能把当前正文配上旧版图谱。首版不另建一套分支星海；在现有知识空间表达版本差异。完整动效语义和纯问答版本处理见配套规范第 6 节。

### 5.3 冲突和撤销

首版采用基准修订与文件哈希检查：请求携带 `baseRevision`、受影响文件及依赖的基础哈希。有关文件或答案变动时返回差异，不静默覆盖；只有无关文件改变时，可重新校验后继续，不让两个不同 DD 的编辑无故互相阻塞。两个窗口与外部文本编辑器都适用这一边界。

个人视图和独立批注不递增文档修订。LLM 提案还记录所依赖的回答版本与来源指纹，避免“正文没变但用户已改答案”的隐性过期。外部改动被观察到并校验后记为新修订；软件关闭期间未留存的中间覆盖稿无法补回，精确批次可通过提交命令记录。

“恢复到某版本”和“撤销某次导入”不是同一操作。撤销较早批次时要识别之后对相关内容的修改，出现冲突先给出处理选择，不能顺便删除后续问答。

## 6. 问询与 LLM 协作

### 6.1 两种问询都必须成立

**批量问询：**用户指定目标和范围，LLM 一次提供一组问题；用户在策问集中选择方案、输入自定义回答、暂缓或指出前提不成立；完成后生成答案包，再由 LLM 提出修改或下一轮问题。

**连续深挖：**用户在外部 LLM 对话中围绕一个方向反复讨论；LLM 可读取新的已提交修订、发布少量后续问题、提交修改草稿。策问同步显示提案和问答记录，用户采纳后进入正式内容。

首版不要求内置聊天模型。外部客户端有能力时可通过 MCP 交互；没有相应能力时，通过导出和导入文件继续。软件不能承诺让任何外部模型自动等待、唤醒或无限持续工作。

### 6.2 一个问题的数据

每个问题有稳定 ID、所属轮次、基于的修订、关联条目、提问原因、问题正文、回答形式、推荐选项和推荐理由。

选项说明选择后的收益、代价和影响；推荐标记只是一种说明，不自动提交答案。支持单选、多选和自由文本，并提供“不符合我的想法”“暂缓回答”“问题前提不成立”。

问题显示编号与稳定身份分离，跨轮次出现“问题 1”也不会覆盖旧问题。首版支持明确的条件式后续题，不做复杂问卷编程器。

用户选项 ID、当时选项文本、自由输入原话、提交时间、回答修订分别保留。模型解释与最终设计决定另存；不能把解释冒充用户原话。改答后保留旧答案并标记依赖它的提案需要更新。

每个可追踪问题有独立的 `docs/questions/*.md`；轮次索引组织这些问题。问题、选项、用户原话、模型解释与采纳依据全部是可直接阅读的 Markdown。多个 DD 关联同一问题，DD 只放问题链接和当前未决边界。采纳后将当前有效规则写回 DD，不让用户必须翻完讨论才知道游戏现在如何设计。

### 6.3 修改提案

提案包括目标内容、前后差异、修改原因、相关答案和来源。界面显示新增 / 修改 / 归档 / 关系变化，并提示波及的直接联系。

用户可以采纳整批、排除独立项、编辑后采纳、退回或拒绝。部分采纳仍须满足关系端点、结构和依赖完整性，不允许留下半条关系。一次连贯修改只需一次审核，无须逐字确认。

提案本身、问询发布和暂存导入可由被授权的 LLM 完成；正式内容提交以用户在界面中的采纳记录为依据。授权绑定实际提案内容指纹和基础修订，模型不能提交一段“用户已批准”的文字来代替采纳。

### 6.4 上下文选择

用户可选全部项目、指定 DD、选中条目、工作分组或问题主题。提供将发送的范围、版本、关联来源和大小预览；个人笔记默认排除，项目批注由用户选择。

大项目用摘要索引、分页读取和按关系扩展获取内容；超限要说明省略了什么，不能静默截断后假装已经理解全项目。即使切换模型或聊天客户端，也可凭项目 ID、修订和问答记录继续。

### 6.5 接入方式与首版交付

| 方式 | 用途 | 首版要求 |
|---|---|---|
| 文件交换包 | 任何能处理文本 / 文件的 LLM | 独立完成上下文 → 问题 → 答案 → 修改提案闭环 |
| CLI | 本地代理或脚本 | 查询、准备导入、提交提案、查询状态，错误结构统一 |
| MCP | 支持 MCP 的客户端 | 读取、搜索、发布问询、读取答案、准备导入、提交提案 |
| Skill / 操作说明 | 让模型知道顺序和边界 | 导入、问询、更新三份流程；没有 Skill 宿主也能读普通说明 |

三种通道共用协议和命令服务，不能形成三套数据逻辑。项目包协议包含 `protocolVersion`、`projectId`、请求 ID、幂等键及适用的内容基准。

## 7. 数据和技术方案

### 7.1 推荐架构

保留现有 Vite + TypeScript + Three.js 前端与可复用的视图代码；拆出领域模型、命令、存储和适配层，不以全面重写 UI 为前置工作。

推荐首版使用 **Markdown 项目目录 + Node 本地服务 + SQLite 索引 / 工作记录 + Electron Windows 壳**。桌面界面、本地浏览器和 MCP 共用文件服务和索引；外部文本编辑器可直接修改同一项目文档。领域模型不依赖 Electron，可保留未来独立部署的可能。

| 层 | 职责 |
|---|---|
| 展示层 | 现有图谱、文档、卡片，以及项目、编辑、问询和版本界面 |
| 应用命令层 | 范围与授权上下文、校验、冲突检测、可恢复批次、幂等和事件通知 |
| 领域层 | 项目、文档、条目、关系、修订、问询、决定与提案 |
| 存储层 | 当前 Markdown、公开版本快照、私有工作记录、可重建索引、附件与备份 |
| 适配层 | 本地 HTTP、桌面桥接、文件包、CLI、MCP |

**网页端的首版含义：**在已启动本地服务的电脑上，用普通浏览器访问完整工作台。它与桌面壳使用同一套项目数据，不需要分别导入一次。发布后的本地服务与 Vite 开发服务是两件事。

“上传一份静态 HTML 就能在任意电脑完整编辑并持续监听任意本地目录”是另外一种产品形态，需要浏览器文件权限与存储方案，不列为首版承诺。首版本地浏览器通过服务访问用户明确打开的项目路径；未来纯网页托管版和云同步可另立里程碑。

桌面与浏览器可同时打开，但由后台协调单实例服务；桌面退出时若仍有浏览器会话，明确提示服务状态。服务不可用时保留草稿并提示重连，不能显示虚假的保存成功。

### 7.2 核心对象

| 对象 | 核心用途 |
|---|---|
| Project | 稳定 ID、名称、格式版本、当前内容修订 |
| Document / Block | Markdown 文件及解析出的章节、段落、稳定锚点；磁盘正文是唯一来源 |
| KnowledgeEntry / System | 引用内容块的知识条目，以及主要系统归属 |
| Relation | 稳定 ID、端点、类型、方向、说明和依据 |
| Source / ImportBatch | 来源快照、哈希、相对路径、标题路径、摘录和映射 |
| Revision / Baseline | 公开版本目录、命名基线、操作者、原因和前后差异 |
| Collection / Tag / SavedView | 工作集合、界面标签、保存筛选和查看偏好，独立于正式文档 |
| Annotation / Marker | 批注、个人笔记、收藏及项目关注项 |
| Inquiry / Question / Answer | 问询主题、轮次、问题和不可混淆的原始回答 |
| Decision / Proposal | 已采纳的决定和待审核的修改建议 |
| Asset | 图片等附件、哈希、引用与相对位置 |

不把显示标题、文件路径、数组下标当成身份。应用版本、数据格式版本、接入协议版本分别管理。

### 7.3 写入与更新

编辑器、CLI 和 MCP 的写入经过同一个命令服务，检查项目归属、ID、结构、引用、基准修订和文件哈希，使用暂存文件、写入日志和备份完成可恢复提交。全部文件校验成功后才发布完整版本；中途失败显示未完成状态并可恢复，不能把它称为成功。项目级幂等键防止重试产生重复项。

外部文件读写也是正式支持的入口。监听事件合并后扫描实际内容，启动与刷新时补扫；识别重命名、删除、重复 ID、解析失败和草稿冲突。不能用旧缓存覆盖磁盘，不能声称普通文件系统能为任意外部程序提供跨文件原子事务。详细恢复状态见目录规范。

界面在收到提交事件后同步刷新相关视图，不通过重载整页保存状态。LLM 提案更新可以即时展示，走提案通道的正文修改在用户采纳后落盘；手工编辑及已授权的外部直接改文件走各自保存与同步流程。

来源保存选定文件的快照和指纹。正式规则、关系和问答直接落入 Markdown；数据库仅保存派生索引和编辑器工作信息。文件解析与界面是同一内容的两个入口，不维护两套可分别编辑的正文。

### 7.4 本地服务与桌面边界

服务默认仅监听回环地址，使用本机会话凭证并校验调用来源，拒绝任意网页驱动本地写入。MCP 进程作为服务适配器，不另开一条数据库写入通道。

桌面采用隔离的渲染进程、最小 IPC、内容安全策略和受控链接打开方式。导入文档中的 HTML / 脚本不能执行；来源正文只是资料，不能作为操作指令。[Electron 官方安全建议](https://www.electronjs.org/docs/latest/tutorial/security)

SQLite 驱动和 Node / Electron 运行时版本在早期打包验证中锁定，存储通过适配器隔离。不能把 `node:sqlite` 预设为稳定无风险接口；当前官方文档仍将它标为候选发布级别。[Node SQLite 文档](https://nodejs.org/api/sqlite.html)

MCP 先支持本地 stdio 连接，适配客户端的能力协商；远程部署另议。不要依赖模型自动唤醒或把采样能力当作问询循环的必要条件。[MCP 官方架构说明](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

## 8. 导入、导出和备份

### 8.1 首版支持的输入

- 策问项目目录 / 完整项目包：当前 Markdown、公开历史、必要工作记录、来源及附件，支持精确保留。
- Markdown 文件或目录：识别标题层级、内部链接、文档和候选条目；展示映射和未识别内容。
- 结构化 JSON / LLM 提案包：经过协议校验进入暂存区。
- 手工粘贴文本：先成为草稿，用户决定结构和归属。

PDF、Word、图片 OCR 不作为首版原生解析必达项。其他工具可先转换为可审阅文本，并明确保留原始来源；不能声称已无损解析不支持的格式。

导入分成预检、审核、可恢复提交、核对 / 恢复四步，详见独立流程文档。普通 Markdown 重新导入依靠显式映射和来源身份判断更新；名称相似只作为候选提示，不自动合并。已经属于项目 `docs/` 的直接修改走文件同步，不要求每次重新导入。

### 8.2 导出类型分开命名

| 导出形式 | 目的 | 内容与限制 |
|---|---|---|
| 当前策划文档 | 给人或 LLM 阅读、直接修改 | 当前 `docs/`、项目说明与相对附件；不包括编辑器私人记录 |
| 协作交换包 | 给 LLM 继续工作 | 指定范围、明确修订、问题 / 答案 / 提案及必要来源 |
| 文档与历史包 | 不依赖策问留存完整策划演进 | 当前公开文件、`versions/` 及其快照和校验清单 |
| 完整项目包 / 备份 | 迁移、恢复和留存 | 公开文件与历史、选定工作记录、来源及附件，包含清单和校验值 |

个人笔记、个人分组和查看偏好单独勾选；对外导出默认不包含私人材料或本机绝对路径。项目备份明确展示包含项，不能把不完整的阅读导出标为完整备份。

导入备份区分“恢复原项目”和“复制为新项目”：前者保留身份与完整历史，且不能覆盖仍在打开的项目；后者从当前或指定修订建立新项目和首个版本，记录复制来源，维护内部引用映射。旧项目历史不改写身份后混入新项目的版本链；需要完整续接旧历史时使用恢复流程。

### 8.3 备份与升级

提供手工备份、轮换自动备份和备份位置设置；在格式迁移、大批导入和恢复前建立恢复点。先协调应用写入，对当前文件做哈希前后核对，遇到外部变动重试或说明待完成状态；再保存一致的工作记录和版本清单。SQLite 工作数据使用一致性备份机制，不能在运行时随便复制数据库主文件就称为完整备份。[SQLite 官方备份接口](https://www.sqlite.org/backup.html)

正式发布后数据格式升级要有备份、迁移记录和失败恢复。当前临时原型没有兼容包袱，但用户正式数据不能因此在升级时丢失。

## 9. 通用示例工程与开发资料处理

建立完全虚构的“基础示例：小型冒险游戏”。内容包含目标体验、基础循环、时间、资源、地图等通用主题，服务于演示关联和问询，不复述真实游戏的专属机制。

不是仅把游戏名称换掉：名称、编号、专有术语、数值、规则组合、来源路径和故事设定都重新编写。来源指向示例自身附带文本，并清楚标注虚构内容。可保持与当前相近的节点和连线密度，以比较封板视觉。

通用示例提供正常情况和少量明确标注的未决问题。重复导入、过期提案、断裂引用等异常材料放入独立验收夹具，不让新用户打开示例就面对损坏数据。

正式工程中区分运行示例、开发夹具与用户数据目录。历史研究报告可以保留为历史材料，但不得打包成产品示例、默认模型上下文或运行依赖。发行前检查公开说明、截图、包内资源和默认路径，排除真实游戏摘录与本机来源路径；未授权自动改写历史 Git 记录。

**当前已有虚构示例基础；正式发行仍须核查运行资源、截图与说明，示例迁移不代表真实游戏已接入。**

## 10. 开发与真实接入隔离

| 工作流 | 使用资料 | 产物 | 谁发起 / 何时开始 |
|---|---|---|---|
| 策问正式开发 | 虚构示例与通用异常夹具 | 软件固定版本、协议、接入说明、验收记录 | 工具开发任务 |
| 战术巫师接入验收 | 用户在游戏任务中指定的真实资料 | 独立真实项目、导入核对和问题记录 | 首版达标后，由用户在游戏策划对话中发起 |

两个流程使用不同工作目录、数据库、项目 ID 和资料范围。开发服务不扫描或自动挂载真实游戏目录。真实验收使用固定发布版本，不能现场修改策问源码来“完成接入”。

接入时工具不足，游戏任务记录版本、步骤和错误；工具开发任务使用整理后的虚构最小复现修复，重新交付版本，随后从接入检查点继续。真实接入通过与否单独记录，示例验收通过不等于真实游戏已通过。

首次真实接入创建工作副本，原 GDD / DD 保持只读。导入策问不等于重写原策划；写回游戏仓库是需要另行明确范围的后续流程。

## 11. 首版范围与后续范围

### 首版必须完成

- 手工建项目，编写与编辑 GDD / DD / 条目，关系维护，附件基础支持。
- 通用示例、持久化、草稿恢复、归档、搜索、个人工作分组、标签、批注、个人笔记、标记和保存筛选。
- 保持封板的多视图与过渡，并与真实数据同步。
- 独立干净的 Markdown 项目目录、直接读写同步、外部编辑冲突处理。
- 公开落盘的文档修订、基线、语义比较、历史阅读、恢复与 3D / 分层版本生长展示。
- 导入预检和映射、审核、去重与重试、导出、备份及恢复。
- 批量问询、连续问答记录、用户自定义回答、提案审核和来源追踪。
- 文件协议、基础 CLI / MCP、Skill 和普通说明，任何单一模型厂商都不是硬依赖。
- Windows 桌面交付和本地浏览器访问；可从干净安装完成通用验收。

### 后续增强

智能工作分组、可自定义模板库、复杂批量重构、多跳关系分析、分支历史展示、实现与试玩证据、更大规模检索、更多文档格式、签名与自动更新能力完善。

### 当前不做

云端账号和同步、实时多人编辑、复杂权限矩阵、Git 式分支合并、内置模型计费与密钥平台、自动改写游戏仓库、新图谱模式和关系矩阵。它们不应成为首版可用的前提。

## 12. 交付顺序与发布门槛

| 阶段 | 交付结果 | 过关条件 |
|---|---|---|
| M0 基线与契约 | 冻结记录、虚构示例、文件格式与版本目录、服务和打包验证 | 文档权威源、身份、服务方式和示例边界明确 |
| M1 手工工作台 | 项目、Markdown 编辑、外部同步、关系、草稿与归档 | 不连模型能写完并重开一个小型 GDD；普通编辑器可往返 |
| M2 整理与版本 | 分组、批注、标记、搜索、公开历史、比较恢复与图谱生长 | 日常整理方便，修改可追溯可恢复且能看见演进 |
| M3 资料交换 | 通用导入、去重、映射、导出和备份 | 合成资料可往返，失败可恢复 |
| M4 LLM 协作 | 问询、回答、提案、上下文和文件闭环 | 人机多轮共同完善同一项目 |
| M5 接入与发行 | CLI / MCP、独立接入包、桌面发行与通用验收 | 固定版本从干净环境完成全部必达场景 |
| A1 独立真实验收 | 战术巫师从游戏对话发起接入 | 不改工具源码完成经授权的真实接入与核对 |

这些是依赖顺序，不是未经验证的工期承诺。可并行准备模板、说明与交互规格；不能在数据与写入契约未稳定前同时实现多套适配器。详细任务与依赖见配套清单。

发布前至少完成类型检查、构建和人工场景验收，并记录实际环境与结果。遵循当前项目偏好，默认不新增或执行自动化测试；后续如另行约定自动化，再决定范围。本方案阶段没有运行构建或测试。

规模验收建议准备约 100 份 DD、1000 个可引用条目、3000 条关系的合成项目，记录加载、搜索、切换和编辑反馈。先在约定设备建立基线，再确认性能门槛；不承诺全量标签同时铺开。采用按系统聚合、按需读取和标签避让保持可读性，已封板的动效节奏不因数据量被任意更改。

**首版完成的定义：用户可独立创作，LLM 可按规范参与，内容可追溯与恢复，真实游戏能在另一条工作流中接入。**
