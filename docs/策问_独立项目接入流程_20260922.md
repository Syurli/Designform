# 策问独立项目接入流程

状态：接入流程草案，2026-09-22。本文用于未来独立验收，现在不执行导入。

## 1. 适用范围与前提

本流程用于把用户指定的既有 GDD / DD 接入策问。第一个真实验收对象计划为战术巫师，但工具开发只使用通用虚构示例。

开始真实接入前必须已经有：

- 固定可运行的软件版本，Windows 桌面与本地浏览器入口。
- 已通过通用验收的手工编辑、文件同步、公开历史、问询、导入和恢复能力。
- 版本匹配的项目文件说明、协议、Schema、CLI / MCP 说明及文件交换替代流程。
- 独立的导入、问询、修改三个 Skill，以及不依赖 Skill 宿主的普通 Markdown 操作指南。
- 明确的已知限制和恢复说明；工具代码不因接入某一游戏临时改变。

具体开发门槛见 [任务与验收清单](策问_开发任务与验收清单_20260922.md)。项目文件边界见 [目录与版本规范](策问_文档目录与版本规范_20260922.md)。

## 2. 谁从哪里发起

由用户在游戏项目的策划对话中发起。该任务先读取已发布的接入说明，按用户已指定范围操作；范围明确时不反复索要相同授权。缺少关键资料范围或目标位置时，只补齐必要信息。

接入任务的 LLM 不需要阅读策问源代码。它使用项目文档格式说明、文件工具或公开 CLI / MCP 接口；这些能力不可用时仍可完成文档和交换包方式。

工具开发任务不主动扫描、复制或接入游戏资料；初版软件也不保存真实游戏源路径作为默认值。

## 3. 两条隔离的工作流

| 项目 | 工具开发 | 真实接入 |
|---|---|---|
| 所在任务 | 策问开发任务 | 用户发起的游戏策划任务 |
| 使用数据 | 虚构示例和异常夹具 | 用户指定的真实资料 |
| 工作目录 | 工具源码、独立开发数据 | 独立策划项目目录 |
| 数据库 / 项目身份 | 开发专用 | 新建真实项目 ID 和工作区 |
| 修改对象 | 工具实现与接入规范 | 策划工作副本及其版本 |
| 验收结论 | 通用能力是否可用 | 真实接入是否成立 |
| 出现问题 | 修复通用能力并交付新版本 | 固定现场、反馈问题、等待修复后续接 |

同一台电脑允许并存，但不能共用默认项目数据库或把真实内容写进开发示例。可以使用不同 Codex 任务，也可以由其他 LLM 客户端参与；隔离依赖工作范围和资料目录，不依赖某个客户端名称。

## 4. 接入前记录

记录以下内容即可开始具体预检，不需要填一份与任务无关的长表。

- 软件版本、文档格式版本、协议版本。
- 源资料清单与本次范围；有多个旧稿时说明已知地位，不凭文件修改时间猜哪份有效。
- 独立目标项目目录、项目 ID、项目说明。
- 是否已有目标文档与未提交草稿；初次接入建议干净目录。
- 使用文件交换、CLI 或 MCP；无连接能力时的替代方式。
- 预计保留的来源、附件与公开问答，排除项及原因。

首次接入将原游戏资料作为只读来源，生成策问项目的 Markdown 工作副本。以后可以直接编辑这份工作副本；写回原游戏仓库不包含在本次默认流程内。

## 5. 四步接入

### 第一步：预检和暂存

扫描用户指定文件，不自动扩大到整个硬盘或聊天历史。建立清单、哈希和来源快照，解析标题、文档、候选知识条目与显式链接。

预检报告至少包括：

- 文件数量、支持 / 不支持的格式、附件情况。
- 拟建立的 GDD、DD、规则条目、关系和问题数量。
- 同一文件重复、同名不同内容、旧规则替代、新旧冲突。
- 缺失 ID、重复 ID、失效引用、无法明确的归属和状态。
- 从原文直接得出的关系，与模型根据文本提出的关系建议分别标明。

此阶段只写暂存候选，不改正式 `docs/`。不把所有段落自动拆成节点；只有需要引用或讨论的规则成为可引用条目。

### 第二步：审核候选结果

展示具体的新增、更新、跳过和待解决项；用户可调整映射、合并候选或保留冲突。只在需要决定的地方提出问题。

来源没有写明的规则继续标为草稿或待确认。推断关系不自动变成设计事实；重复编号不能自动当作同一身份。

审核结果绑定实际候选包指纹、目标项目及基础版本；之后候选内容改变，原审核不能套用。软件里确认过的完整批次无需换个通道再次重复确认。

### 第三步：可恢复提交

准备当前 Markdown、关系段、问题文档、来源说明和附件，校验 ID、目标路径与引用。建立导入前恢复点；通过事务日志和文件哈希保护批次写入。

多文件写入完成并核对后，发布导入版本及公开快照，记录导入批次与摘要。失败显示未完成并提供恢复，不把部分成功伪装成整批成功。

同一请求重试返回已有结果或续接同一批次，不创建重复文档。直接文本编辑器不受进程锁控制，因此提交过程中发现第三方新内容时保留双方并处理冲突。

### 第四步：核对、继续或恢复

核对实际文件清单与数量，抽查主要规则、跨 DD 关系、问题原文和附件；在文档、卡片、3D / 分层和关系分析中定位同一条目。

从普通文件编辑器阅读 `docs/` 和导入版本快照，确认无源码或私有数据库依赖。查看版本差异，确认新增节点和关系的生长对应真实变化。

需要撤销时，预览本批次之后的修改，再形成恢复版本；不得直接删除后来新增的回答。核对完成后决定继续导入剩余已授权范围，或者先完成下一轮问询。

## 6. 第一次真实验收如何控制范围

先选择能覆盖 GDD、两份以上关联 DD、一个跨 DD 问题和少量附件的小批材料，走完全部流程。这个小批是验证范围，不代表工具只支持小项目。

用户若已明确要求全量接入，在小批核对通过后按同一范围继续；否则由用户在游戏任务中决定扩大到哪些资料。不能把“允许访问这台电脑”当作“重写全部策划”的许可。

实际验收要包括：

1. 原资料未被改变，独立项目的 Markdown 可读可写。
2. 同批重试无重复；重命名不换身份；来源缺失和冲突可见。
3. 用户手工修改后，LLM 的过期提案不会覆盖它。
4. 批量问询、自定义回答、连续追问及决定落实能够完成。
5. 换另一个 LLM，只提供项目说明和公开文档仍可继续。
6. 当前文档、公开版本与图谱一致；生长与差异展示表达真实变化。
7. 备份在干净位置恢复，历史与附件有效；私人内容按选定范围保留。
8. 开发示例与真实项目不串写。

未解决的游戏设计问题不自动等同于工具缺陷。只要工具正确保留未决状态，就可以继续推进设计讨论。

## 7. 接入后的日常协作

### 手工与外部直接编辑

用户可在策问里编辑，也可直接修改 `docs/`。LLM 已被用户授权直接修改指定文件时，无需为了普通 Markdown 编辑再阅读策问代码或强制走 MCP。

直接写文件已经是对工作副本的修改，不可能由 UI 事后阻止；策问负责同步、留存观察到的版本、发现冲突和显示来源。需要“先提案后采纳”的场景，应使用提案文件或受控接口，不让模型先改正式文件再假称仍待审核。

### 问询与更新

LLM 读取限定范围和当前修订 → 发布问题 Markdown 或问题包 → 用户在策问回答 → 答案写入问题文档 → LLM 读取答案 → 提交修改建议 → 用户采纳 → 更新相关 DD 和落实记录 → 生成版本。

批注默认留在编辑器；需跨 LLM 持续讨论的内容明确发布为问题。问题的推荐方案、原始回答、模型解释和最后决定不能合并为一段不知是谁说的结论。

### 版本记录

策问保存、受控批次、有效外部修改都会产生相应版本记录。需要准确区分多文件的一次迭代时，使用配套提交命令或界面整理批次。

关闭本地服务后多次覆盖同一 Markdown 的中间状态不会自动存在；希望精确保留每轮时，应每轮显式执行版本提交并确认成功。持续运行服务只能记录实际观察到的稳定状态，快速连续覆盖仍可能被合并；不要把最终文件的修改时间当作完整历史。

## 8. 失败和缺陷回流

| 问题 | 接入侧处理 | 开发侧处理 |
|---|---|---|
| 文档含糊、规则互相矛盾 | 保留原文，提出策划问题 | 通常不改工具 |
| 不支持的格式 | 报告范围，选择先转文本或跳过 | 是否扩展支持单独评估 |
| 文件同步 / 导入 / 版本错误 | 保留批次与现场，暂停受影响操作 | 用虚构最小复现修复并发布新版本 |
| 手工与模型冲突 | 比较并选择 / 合并，保留双方 | 若冲突显示不正确再报缺陷 |
| 数据写入中断 | 使用恢复流程，不盲目重跑 | 若恢复能力缺陷则修复再续接 |

缺陷报告包含版本、操作步骤、预期 / 实际、错误码、影响范围和整理后的最小复现。真实游戏资料不直接复制进工具仓库；确需真实片段定位时，在原游戏工作流中限定范围处理。

工具开发交付新固定版本后，先用通用夹具验证，再由游戏任务从保留检查点恢复。不能在接入过程中偷偷改源码、改数据库或删文件后宣称旧版本已经验收通过。

## 9. 最终接入报告

记录实际接入的软件版本、资料范围、目标项目、导入版本、数量核对、问询轮次、恢复检查与未决事项。结果分为：

- 通用工具已通过的能力。
- 本次真实项目已通过的流程。
- 尚未覆盖的资料 / 功能。
- 未决设计问题。
- 需要修复的工具缺陷。

当前没有执行本流程，也没有建立战术巫师正式项目。真实验收必须由用户在后续游戏策划任务中发起。
