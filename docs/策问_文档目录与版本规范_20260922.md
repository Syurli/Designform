# 策问项目：文档目录与版本规范

状态：正式开发目标规范；基础快照已有实现，完整版本管理与可视化尚待验收。日期：2026-09-22。

## 1. 基本约定

**Markdown 文件是策划内容的权威源。** 策问编辑器、外部文本编辑器、用户和 LLM 都围绕同一份文件工作；数据库是索引和编辑器辅助存储，不保存一份与 Markdown 各自独立修改的正式正文。

项目不需要置于策问源码目录，也不依赖原聊天记录。把项目说明、`docs/` 和必要附件交给另一个 LLM，它就应当能够理解和修改策划。需要追溯时再提供 `versions/`，无须阅读策问代码、数据库或前端资源。

以下结构属于建议的首版文件契约。具体文件字段在 M0 固化，之后由独立格式说明维护，不依赖实现细节。

## 2. 一个项目就是一个独立目录

```text
我的游戏/
├─ PROJECT.md                         项目名称、稳定 ID、格式版本、阅读入口
├─ docs/                              当前有效的策划与协作文本
│  ├─ README.md                       面向用户和 LLM 的读写说明、导航
│  ├─ gdd/
│  │  └─ GDD.md                       当前总纲、系统归属和 DD 目录
│  ├─ dd/
│  │  ├─ DD-001_资源系统.md
│  │  └─ DD-002_时间系统.md
│  ├─ questions/
│  │  ├─ INDEX.md                     问询轮次及未决问题索引
│  │  └─ Q-001_休息是否消耗资源.md
│  └─ assets/                         当前文档使用的相对路径附件
├─ versions/                          公开、可独立阅读的版本历史
│  ├─ INDEX.md                        可重建的版本时间线与基线导航
│  ├─ BASELINES.md                    命名基线及其变更的公开记录源
│  ├─ V000001/
│  │  ├─ README.md                    时间、来源、上版、修改原因与摘要
│  │  ├─ manifest.json                文件清单、哈希、稳定修订 ID
│  │  ├─ PROJECT.md                   当时的项目说明
│  │  └─ docs/                        该版本的完整文档及附件快照
│  └─ V000002/
│     ├─ README.md
│     ├─ manifest.json
│     ├─ PROJECT.md
│     └─ docs/
└─ .cewen/                            编辑器工作区，不要求 LLM 读取
   ├─ index.sqlite                    文档解析结果、检索与关系索引，可重建
   ├─ workspace.json                  批注、分组、标签、提案；网页/桌面共用
   ├─ views/                          镜头、布局、筛选、阅读位置
   ├─ cache/                          可重建的历史图谱与版本差异缓存
   ├─ personal/                       私人笔记、收藏和个人标记
   ├─ drafts/                         尚未提交到正式文档的草稿
   ├─ transactions/                   多文件提交和恢复日志
   ├─ imports/                        暂存候选内容、来源快照及映射
   └─ logs/                           编辑器诊断记录
```

`docs/` 不放页面布局、三维坐标、缓存、SQL、组件配置、MCP 实现或运行日志。历史版本位于同一项目根目录下，但不堆进当前 GDD / DD 文件夹，避免模型误读旧稿。

版本目录按需读取，不把所有历史自动塞入 LLM 上下文。工作区日志和私人材料默认不进入外部协作范围。

备份保存在用户指定的另一个目录，防止备份套备份、项目包无限膨胀。完整项目备份包含需要保留的编辑器工作记录；发布给别人阅读可以只提供公开文件。

## 3. 各类数据的归属

| 数据 | 正式保存位置 | 能否不依赖策问阅读 / 恢复 |
|---|---|---|
| GDD、DD、规则正文、设计状态 | `docs/gdd`、`docs/dd` | 可以 |
| 正式系统归属、DD / 规则之间的关系 | GDD 的结构和 DD 内的语义关系段 | 可以 |
| 已发布问题、推荐方案、用户回答、模型解释、决定记录 | `docs/questions` | 可以 |
| 当前有效的最终规则 | 对应 DD 正文，附问题来源链接 | 可以；不能只留在问答记录里 |
| 历史正文、历史问答、关系变更、版本链及命名基线 | `versions/` | 可以 |
| 项目 / 个人工作分组、收藏、界面标签、保存筛选 | `.cewen` | 不属于 GDD；随完整备份迁移 |
| 片段批注、回复、风险标记、个人笔记 | `.cewen` | 不承诺仅凭 `docs` 恢复 |
| 需要跨 LLM 继续讨论的批注 | 用户明确“发布为问题”后写入 `docs/questions` | 发布后可以 |
| 正文中必要的解释与设计依据 | 对应 DD 或问题文档 | 可以 |
| 未采纳提案、输入草稿、事务日志 | `.cewen` | 需要完整备份；不是可随意删除的缓存 |

**“编辑器与文档分离”不等于“编辑器数据都没有价值”。** 只把 `index.sqlite` 和明确标注的缓存视为可重建。未完成事务恢复前不得清理工作区。

删除整个 `.cewen` 后，可根据公开文件重建当前内容、历史版本、正式关系、已发布问答和命名基线；会失去未公开的批注、分组、私人笔记、草稿和未采纳提案。用户执行此操作前必须知道该差别。

## 4. Markdown 保持可读，只加入必要身份

### 4.1 最少元数据

项目说明保存稳定项目 ID 和文档格式版本。GDD / DD / 问题文档只在短 YAML 头部保存文档 ID、类型、设计或问题状态等语义字段；不加入编辑器布局数据。

文件名编号用于阅读和排序，文档 ID 用于身份；改标题和文件名不换身份。普通 Markdown 无元数据时也可打开阅读。接入时若要建立稳定引用，由用户预览添加 ID 的变更，不能读一次文件就偷偷重写整篇文档。

只有需要成为知识节点或被精确引用的规则设置稳定锚点；普通段落保持普通 Markdown。建议采用简短显式 HTML 锚点与正常标题：普通 Markdown 支持原始 HTML 语法，应用仍须对渲染内容做安全过滤，只允许必要锚点等安全元素。[CommonMark 规范](https://spec.commonmark.org/0.31.2/#raw-html)

稳定身份不随标题、章节位置、显示编号变化。复制条目应产生新 ID；重复 ID、锚点删除与冲突必须报告。应用解析时保存原始文本范围，修改某一段不重排用户整份文件的换行、表格或未识别内容。

### 4.2 DD 示例

下面全部为虚构演示；短 ID 仅用于说明，正式新建由工具生成项目内唯一身份。

```markdown
---
id: dd-resource-01
type: dd
status: draft
---

# 资源系统

## 设计目标
让玩家在探索收益与休息成本之间作出选择。

<a id="rule-rest-cost"></a>
## 休息成本
当前方案待确认：休息是否消耗补给，仍需完成下方问询。

### 关联设计
| 关系 ID | 类型 | 目标身份 | 目标 | 依据 |
|---|---|---|---|---|
| rel-rest-time | 依赖 | dd-time-02 / rule-time-step | [时间推进](DD-002_时间系统.md#rule-time-step) | 休息行为需要确定时间消耗。 |

### 相关问题
- [Q-001 休息是否消耗资源](../questions/Q-001_休息是否消耗资源.md)
```

关系行属于所在规则的出向关系，方向、ID 和说明都可直接阅读。跨 DD 关系只保存一份，反向列表由编辑器推导，不要求用户维护两份一致的反向表。文档整体的关系放在文档级关联段。

正式关系保留目标文档 ID 与可选条目 ID，普通相对链接负责阅读。GDD 的系统归属和问题的目标引用也使用同一身份约定，不能把目标身份仅存在私有索引中。这样外部重命名且旧索引丢失时，仍可通过扫描文档 ID 找回目标，并提出链接修复。无法唯一识别时提示断链，不猜测目标。

### 4.3 GDD 示例

GDD 主要包含目标体验、核心循环、系统目录、整体约束和跨系统未决问题入口。系统分层以 GDD 中明确的结构为依据，不能仅凭工作分组或 3D 坐标推断。

允许 DD 同时与多个系统相关，但指定一个主要归属；其他联系写为普通关系。归属结构禁止成环，普通知识关系允许成环。

## 5. 问题独立文档，最终规则回到 DD

### 5.1 推荐选择

**一个需要追踪的问题对应一份问题文档；问询轮次负责组织，不把整轮当作一个不可拆分的问题。** 可在 `questions/INDEX.md` 按轮次列出多个问题。这样跨 DD 的问题只保存一次，下一轮继续同一问题时也不会复制出多个“同名问题”。

DD 内保留“相关问题”链接及一句当前未决边界；不塞入全部聊天记录。小幅措辞修改无需创建问题文件，编辑器批注足够。复杂到需要推荐方案、用户回答和采纳记录时再正式发布问题。

### 5.2 问题文档包含什么

```markdown
---
id: question-rest-01
type: question
status: open
---

# Q-001：休息是否消耗资源？

## 问题背景
基于版本：V000003。
问询轮次：ROUND-001。
相关设计：
- [资源系统](../dd/DD-001_资源系统.md#rule-rest-cost)，目标：dd-resource-01 / rule-rest-cost。
- [时间系统](../dd/DD-002_时间系统.md#rule-time-step)，目标：dd-time-02 / rule-time-step。
当前缺口：资源成本和时间成本之间的关系尚未确定。

## 可选方案
- A：消耗补给。推荐理由：使休息与探索共享资源约束；代价：增加资源管理压力。
- B：只消耗时间。收益：规则简洁；代价：需要明确时间压力从哪里来。
- 自定义 / 暂缓 / 问题前提不成立。

## 用户原始回答
尚未回答。推荐选项不代表用户已选择。

## 模型解释
尚未形成。后续解释必须注明依据的回答 ID，并标为候选。

## 决定记录
尚未采纳。

## 文档落实
- 资源系统：待回答后决定是否修改。
- 时间系统：待回答后决定是否修改。
```

用户提交回答时写入回答 ID、实际时间、选项及当时文本、自定义原话；改答新增一条并指明替代哪条回答。模型解释另立记录，不能改写用户原话。当前文件仍允许直接编辑，因此过去原文最终由版本快照保证可追溯，不假设 Markdown 本身不可修改。

“已决定”和“已落实”分开。一个问题影响三个 DD，必须逐项检查；只改了一份不能标记全部落实。决定采纳后，有效规则进入相关 DD，问题文档保留讨论与采纳依据。

外部编辑中写入“已采纳”是文档状态声明，不构成调用受控 API 的授权凭证。策问显示其来源为外部文件变更；MCP 提案的采纳仍依赖实际界面操作记录。

## 6. 版本必须落盘，也必须能看懂

### 6.1 版本定义

- 未提交草稿：输入过程的可恢复工作，不等于一个正式版本。
- 内容修订：一次完整保存、导入应用、问答提交、已采纳修改，或观察到的有效外部修改批次。
- 命名基线：为一个修订标记“首次评审版”等名称，不复制第二套正文。
- 设计状态：某条规则是否确认，独立于上述版本层级。

首版保留线性修订链。每个修订具有稳定身份，`V000001` 等文件夹名是人可读序号。版本说明包含父修订、作者或来源、时间、修改原因、涉及文件、内容类型和摘要。无可信操作者信息的外部改动标记“外部编辑”，不冒认由用户或某个模型完成。

自动保存草稿与提交版本分离；保存按钮提交，用户也可开启“停止输入后自动提交”的策略。连续输入按批次合并，不能每个按键产生一个目录。问答、导入和提案采纳各自形成明确批次。

**版本记录从项目第一次正式保存起生效，不等到版本界面完成后才开始保存。** 内容没有变化的重复保存不产生空版本；保存失败或只完成部分文件时不产生“成功版本”。界面应区分草稿已保留、正在提交、正式版本已完成及提交待恢复。

版本追溯有三个入口，但共用一条项目修订链：

| 入口 | 用户查看的内容 | 数据依据 |
|---|---|---|
| 项目历史 | 某一时刻整套 GDD、DD、关系、问答及附件 | 该项目修订的完整快照 |
| 文档历史 | 某份 GDD / DD / 问题的新增、编辑、改名、移动及删除 | 按稳定文档 ID 筛选项目修订，不另外维护一套 DD 版本号 |
| 条目历史 | 一条规则的正文、状态、归属和关系怎样变化 | 按稳定条目 ID 对照各版文档；普通未设锚点段落提供文档差异，不猜测身份 |

版本关系与设计关系分开表达。版本清单记录“此版接续哪版”；恢复操作另外记录“内容恢复自哪版”，不能把恢复来源冒充父修订。例如从 V000006 恢复 V000002，得到 V000007，父修订仍是 V000006，恢复来源是 V000002。问询、导入及已采纳提案可记录对应的公开来源 ID，模型身份无可靠记录时不得猜测。

### 6.2 历史结构与可读性

`versions/INDEX.md` 提供按顺序阅读的版本表和命名基线入口。`versions/BASELINES.md` 是基线名称、对应稳定修订 ID 及改名 / 取消记录的公开来源，不只放在可重建索引里。每个版本目录中的 `README.md` 提供可读变更说明，并链接上一个版本及该版本的 GDD。

首版优先完整快照，含当时的当前文档与所需附件，保持相对链接可用。`manifest.json` 供校验和工具重建使用，用户或模型日常读策划无需先理解它。不会要求模型执行 Git 命令或查询数据库才能看旧稿。

完整快照会占用额外空间，首版显示历史容量并提供备份，不自动删除用户版本。历史清理与附件去重等优化可后续设计，须保持版本链可解释，不能破坏普通目录独立阅读或让历史附件跟随当前文件一起变化。

版本快照发布后应用不修改正文；新增基线等历史索引信息独立记录。直接手工改动历史快照时，根据哈希检测并显示“历史文件已被修改”，不能把它作为可信原快照继续展示。历史文件不是防篡改安全设施，也不承诺能防止用户在磁盘中删除它们。

恢复旧稿：先验证完整性和该快照 `PROJECT.md` 中的格式版本 → 读取选定历史快照 → 预览对当前文档和后续问答的影响 → 写入当前 `docs/` → 创建新的恢复修订，注明恢复自哪个版本。格式不支持时先迁移候选副本或明确拒绝，不能硬套当前解析规则。旧版本仍保留，用户回答和决定的后续记录不得无提示删除。

当前稿已包含草拟改动但尚未完成一致提交时，版本轴标为“工作中”，不把磁盘当前状态冒充已完成版本。

恢复完整备份保留原项目身份与历史；“复制为新项目”则以选定当前稿或修订建立新身份和首个版本，记录复制来源。不能给历史快照强换项目 ID 后仍声称它是未经改动的原历史。

### 6.3 3D 生长与版本切换

沿用封板的 3D / 系统分层主切换，增加版本时间轴或版本选择器。版本能力进入现有知识空间，不新增第三种主总览。

首版必须提供：

1. 当前稿、任意历史版本、两个版本比较的入口；历史状态清楚标注只读。
2. 固定相同节点的布局位置，按稳定 ID 匹配，避免每换一版就整体洗牌。
3. 新增节点从所属系统或关联节点附近显现，新增连线逐步延伸；新增项目根节点没有既有来源时从其布局位置显现。
4. 修改节点保持身份与位置，用短暂高亮及差异详情提示；标签和正文更新不伪装成删除再创建。
5. 删除 / 归档节点在比较过程中保留轮廓与说明，随后收拢淡出；最终选定旧版时显示旧版本本来存在的内容。
6. 系统归属变化平滑移向新分层位置，关系新增、移除或类型变化可单独查看。
7. 时间轴可以逐版播放、暂停、上一版、下一版；切换到纯问答变化时显示“本版无图谱结构变化”，并提供文字差异入口，不制造假生长。
8. 快速拖动时间轴时取消过期目标，从当前显示状态收敛到最新目标；减少动态效果设置提供直接切换。

动效用于表达变化，不演成重新进入页面。最终节奏沿用当前已确认的克制风格，在专门验收中微调；现有 3D ↔ 分层的动效不被修改。复杂的分支宇宙、跨分支合并和全量历史常驻星海不列入首版。

版本演进展示还须遵守以下语义：

- 版本时间轴表达修订先后；画布继续表达所选版本内部的策划关系。不要把每个版本复制成一团同时常驻的星系。
- 文档、卡片、关系分析和搜索结果跟随同一个选定版本。查看历史时，侧栏正文、关系目标和附件都读取历史快照；回到最新后再编辑，不能出现旧图配新文的混合状态。
- 单版阅读只显示该版的真实状态。比较状态可短暂显示已删除内容的轮廓，并标注它属于比较的另一端；不能把轮廓当成当前仍有效的规则。归档是状态变化，是否隐藏遵循归档筛选，不等同删除。
- 改名保留节点身份；只改变正文就高亮正文变化；只改变连线就展示连线变化。布局调整不计入策划修改，问题答案改变也不自动当作规则已改变。
- 相同节点的位置、镜头和选择尽量连续。布局结果与动画缓存放在 `.cewen/views/`、`.cewen/cache/`；清除缓存后由稳定身份重新构建，仍可比较和播放历史，不依赖原机器的缓存。默认布局不得使用每次打开都不同的随机种子。
- 初次打开直接展示选定版本，不强制播放整段历史。用户主动播放演进时再逐版展示，点击变化节点可暂停并查看差异；播放期间不自动追随新的外部提交而跳到其他版本。

### 6.4 一次完整迭代的示例

以下仅为虚构操作，用来验收内容历史与动画是否一致：

| 版本 | 实际修改 | 历史图谱应呈现 |
|---|---|---|
| V000001 | 建立 GDD 和资源 DD | 初次打开静态显示初始结构 |
| V000002 | 新建时间 DD，并增加一条依赖关系 | 新文档节点展开，新增连线延伸；原节点保留 |
| V000003 | 修改资源规则，将它移至另一主归属 | 同一节点移动并提示正文差异，不消失后重新创建 |
| V000004 | 用户回答一个问题，尚未采纳任何规则修改 | 问答出现可读差异；无结构变化时不制造生长 |
| V000005 | 恢复 V000002 的内容 | 新建恢复修订，保留 V000003、V000004 的历史；提交前明确提示当前问答会受影响 |

用户既能从时间轴查看 V000002 的完整策划，也能从资源 DD 打开“此文档历史”，或从一条规则查看其变化。任意两版比较呈现两端的净变化；只有逐版播放才展示中间曾新增又删除的节点，不能从两个相同端点捏造中间过程。

## 7. 文件与编辑器如何同步

### 7.1 外部读写是正式入口

用户可用任意文本编辑器或让 LLM 直接改当前 `docs/`；打开策问后解析最新磁盘文件，不用旧缓存覆盖。`versions/` 供历史阅读，正常修改发生在 `docs/`。

文件监听只用于发现变化，经过短暂合并后用文件哈希确认实际内容；在启动、重新获得焦点、监听恢复及手工刷新时重新扫描补漏。不能认为每次监听事件对应一次完整保存，或认为没有事件就没有改动。[Node 文件监听注意事项](https://nodejs.org/api/fs.html#caveats)

外部编辑尚未保存完整、引用暂时失效或格式异常时，保留原文件并提示“磁盘已变化，部分内容待解析 / 核对”。上次有效图谱可以继续查看，但明确显示它已落后，不能伪称同步完成。重新扫描不是自动修正文档。

同一文件有编辑器草稿和外部改动时，以共同基准、磁盘当前稿、用户草稿进行三方比较；禁止无提示覆盖。首版可保守地让用户确认合并；没有冲突的不同文件修改可重新验证后继续。

外部移动、删除文档不能被缓存“复活”；找到稳定 ID 后更新索引，对断链给出待修复清单。不能靠标题相似度自动合并两个 DD。

### 7.2 批量写入与恢复

文件系统上的多文件修改不能假设像单个数据库事务一样原子完成。采用事务日志、修改前哈希、原文备份、候选文件、逐文件替换和恢复状态，保证可检测、可继续或可撤回。

受控提交流程：准备所有候选内容 → 校验引用与基础哈希 → 写入暂存快照和日志 → 再校验并逐文件落盘 → 核对最终文件 → 发布完整版本目录和索引 → 刷新编辑器视图。

正式版本目录先在暂存位置准备，完整并校验通过后再发布。`manifest.json` 中的完成记录最后生成，包含完成状态、项目和修订 ID、父修订、格式版本、文件清单与哈希；清单覆盖快照正文、附件和说明，不把清单自身纳入自身哈希。只有完成记录存在、身份与父链有效、文件齐全且哈希一致的目录，才进入正常版本轴。缺失完成记录或校验失败的目录标记未完成 / 损坏并提供恢复入口，不凭目录名认定成功。

`versions/INDEX.md` 由完成版本与 `BASELINES.md` 重建。应用读取不把自身尚未完成的事务当作一致版本。第三方直接读文件仍可能看到逐文件写入的中间状态，因此多文件协作优先使用批次提交或等待完成信号。

崩溃恢复时，只对仍匹配预期哈希的文件继续或撤回。出现第三种内容，说明可能有新的外部编辑，进入冲突处理，不能用旧备份直接覆盖。进程内互斥不能阻止其他编辑器写磁盘；文件备份和恢复检查不可省略。

普通外部编辑不能被强迫调用协议。策问在文件稳定后记录观察到的修改；跨文件短暂断链保留待核对状态。需要精确记录一整批外部操作时，提供独立 CLI / MCP 的“开始批次—完成提交”，以及界面“整理为一个版本”的入口。

### 7.3 记录边界

策问运行时，可以记录成功保存和观察到的稳定外部批次。它关闭期间，用户把同一文件覆盖十次而没有留副本，下次打开最多看到最终内容，不能凭空恢复十个中间版本。

需要精确保留每轮时，每轮显式使用配套提交命令生成快照并确认成功。保持本地服务运行能记录观察到的稳定状态，但快速连续覆盖仍可能被监听合并，不能代替明确提交。可选接入 Git 属后续增强，不作为普通用户使用版本功能的条件。

## 8. 独立 LLM 的最短工作说明

项目模板附带的 `docs/README.md` 必须让模型仅凭本项目即可完成工作，至少说明：

1. 先读当前 GDD 和任务指定 DD；不要自动遍历全部历史。
2. 保留文档 ID、规则锚点、用户原始回答；改名时检查相对链接。
3. 普通编辑在 `docs/`；不要改历史快照或 `.cewen`。
4. 未确定内容保持待定；问询文件保存选项与原始回答，DD 保存当前规则。
5. 相关问题只引用一次；跨 DD 问题共享同一文档。
6. 需要用户决策时提交建议；用户明确授权直接修改文件时按指定范围执行。
7. 涉及多文件时先列计划并确认基准，修改后报告受影响文件和仍未解决的问题；可用配套提交工具明确批次。

基础读写不依赖 MCP。MCP 和 Skill 提供更稳妥的范围、提案与提交能力，并不是把文档藏到软件里面的理由。

## 9. 这份规范的首版验收

- 只给另一个 LLM 项目说明与 `docs/`，可阅读、提问、改文档，无需源码。
- 关闭软件修改 Markdown，再打开同步正确；旧索引不会盖回新文件。
- 软件运行期间有外部改动，能够显示差异、冲突及相应版本。
- 当前文件、版本快照和问答可在普通编辑器独立阅读，附件相对路径可移植。
- 只删可重建索引后恢复一致；移除整个工作区时明确哪些个人内容会丢失。
- 任意历史版本的图谱和文档一致，版本比较能正确区分新增、修改、移动、删除与仅问答变化。
- 快照损坏、批量写入中断、重复 ID、外部重命名和失效引用有明确恢复路径。
- 当前示例和真实项目分别在独立目录，源码与运行数据互不嵌套。
