# MCP 能力覆盖审计

更新日期：2026-09-24。对象：应用 0.7.1、文档格式 1、接口协议 1。

本文最初审计 0.7.1 的 12 工具实现；本轮已按审计结论完成第一阶段修复。当前 MCP 注册 20 个工具，重点补齐 LLM 在策划协作中的信息完整性、可追溯性、图文读取与恢复计划读取，同时继续保留用户决策边界。

## 1. 当前结论

当前 MCP 已覆盖 LLM 日常策划协作需要的主要闭环：

**识别项目 → 检查当前状态 → 搜索/分范围读取 → 查看图片 → 发布问询 → 用户作答 → 提交候选 → 查询采纳状态 → 核对历史与恢复信息。**

目标不是把应用每个按钮直接暴露给模型。用户作答、采纳模型提案、任意正式提交、恢复执行、私人工作区读取、项目目录选择等仍保留在人工作业或明确授权的外部文件流程中。

## 3. 本轮已修复的问题

### 当前状态与并发基准

`ProjectService.context()` 现在返回 `fingerprint`、`recoveryRequired`、`diagnostics`、公开 `files` 哈希，以及带哈希的项目入口。新增 `cewen_status` 提供不携带正文的轻量状态检查。

因此模型在提出修改前可以判断当前稿是否处于恢复、文件变化或外部批次状态，并取得 `PROJECT.md` 与其他公开文件的实际并发基准。

### 上下文范围贯通

MCP 的 `cewen_context` 已透传：

- `documentIds`
- `nodeIds`
- `collectionIds`
- `annotationIds`

服务端继续验证条目、分组与批注归属。工作区批注只有显式选择且 `scope === 'project'` 时才进入上下文，私人笔记不会因为工具扩展而默认暴露。

### 大文档读取

新增 `cewen_read_document`。调用者可以使用 `offset` / `limit` 精确续读单份当前文档，不必在完整上下文和 4 MB 上限之间二选一。返回值同时携带文档哈希、总长度、`hasMore`、当前诊断与恢复标记。

### 提案结果查询

新增 `cewen_proposals`。服务只投影项目级 proposal，不返回私人批注、分组、视图等 workspace 内容。结果包含提案状态、原候选 payload、`appliedFiles`、创建与更新时间，可用于跨会话核对部分采纳和最终落实。

### 图片附件实际读取

新增 `cewen_asset` 与受控服务投影。读取范围限定为当前已打开项目的 `docs/assets/`，只接受 PNG、JPEG、WebP、GIF，单张上限 5 MB。MCP 返回真实 image content 和路径、修订、字节数、SHA256 元数据。

这解决了“模型只看见 Markdown 图片路径却误以为已经看图”的问题。非图片附件和任意本机路径仍不开放。

### 历史、基线、备份与恢复计划

新增命名基线、备份状态、恢复计划和撤销计划的 MCP 读取入口。恢复与撤销工具只生成 `CommitRequest` 候选，不执行写入；最终决定仍由用户在工作台完成。

### 说明一致性

接入说明的应用版本已从旧的 0.4.0 修正为 0.7.1；提案错误说明也改为准确描述“公开 Markdown 与受控伴随 JSON”，不再错误宣称只支持 Markdown。

## 4. 继续保留的权限边界

以下没有作为“缺功能”直接开放：

- **用户答案**：LLM 可以发布问题和读取已经写入问题文档的答案，但不能代填或改答。
- **提案采纳**：LLM 可以提交和查询提案，但不能调用 `accept-proposal` 批准自己的候选。
- **任意 commit**：MCP 不提供通用正式文件提交接口。
- **恢复执行**：只提供恢复/撤销计划，不提供直接应用计划。
- **私人 workspace**：不提供整个 `.cewen/workspace.json`；只允许上下文中显式选择项目级批注，以及经过过滤的项目级提案。
- **任意磁盘读取**：图片读取严格限制在项目附件目录；项目创建/打开和导出目的地仍由用户选择。
- **界面状态**：主题、三维视角、阅读位置等不属于正式设计，不需要复制为 LLM 工具。

`begin-batch` / `end-batch` / `checkpoint` 仍只服务于用户已经授权的外部文件编辑。它们不会赋予 MCP 任意文件写入能力。

## 5. 仍可继续演进的项目

以下属于后续增强，而不是当前策划闭环的阻断项：

1. 为历史快照增加与当前文档相同的分段读取，避免极大历史版本一次返回。
2. 如确有生产需求，为非图片附件增加受控文本/PDF读取；保持类型和大小白名单。
3. 如未来需要模型协助创建项目或导出，先设计明确的用户确认与目录授权流程，而不是开放任意路径参数。
4. 可增加 MCP resources/prompts 作为协议与开场白的发现入口；当前 Skill 和工具描述已经可以完成协作。
5. 为 MCP 建立独立的端到端测试夹具，覆盖 tools/list、上下文范围、私人范围拒绝、图片 content、提案状态和恢复计划。

## 6. 验收要求

本轮代码合并前至少满足：

- TypeScript 类型检查及桌面、网页、运行时构建通过。
- `tools/list` 能看到 20 个工具及正确 schema。
- 当前状态能反映 `FILES_CHANGING` / `EXTERNAL_BATCH_OPEN` / recovery。
- `cewen_context` 的四种范围选择均正确，私人批注被拒绝。
- `cewen_read_document` 的 offset、limit、hasMore 正确。
- `cewen_proposals` 不泄露其他 workspace 项。
- `cewen_asset` 拒绝项目外路径、非图片类型和超过上限的图片。
- 恢复/撤销工具只返回计划，不执行正式修改。
- 用户作答、提案采纳和任意 commit 仍未出现在 MCP 工具面。

独立 GitHub Pages 版仍不伪装成 stdio MCP 服务；桌面版和独立网页版继续共用项目格式与核心业务规则。
