# MCP 能力覆盖审计

审计日期：2026-09-24。审计对象：应用 0.7.1、文档格式 1、接口协议 1。

源码基准：[`6f801c4d6d3657f44494333d85f4046f961326d1`](https://github.com/Syurli/Designform/commit/6f801c4d6d3657f44494333d85f4046f961326d1)。本文是该版本的静态源码审查记录，不代表后续版本的工具清单，也不代表已完成 MCP 运行时验收。

## 1. 结论与口径

**当前 MCP 没有开放应用的全部功能。它提供的是以公开文档、问询和人工审核提案为中心的协作接口，而不是完整的应用自动化接口。**

同时，不能把“没有专用工具”直接认定为“完全不能操作”：对白、色板、分类、文档层级、正文引用和公开伴随文件，部分可通过通用文本提案表达。反过来，界面已有的功能、CLI 命令或宿主的文件访问能力，也不能计入 MCP 自身的覆盖率。

本次按 `MCP 注册及参数 → HTTP 路由 → 项目服务 → 文件校验与公开格式` 核对。覆盖分为四类：

- **直接开放**：存在可调用工具与对应服务路径。
- **提案覆盖**：可通过受控文件变化表达，仍需用户审核，不等于已有专用领域操作。
- **尚未开放**：业务或界面已有能力，但当前 MCP 缺少相应入口或参数。
- **有意保留**：人工作答、采纳及私人工作记录等，不应为了工具数量而直接放开。

本文不以“工具数 / HTTP 路由数”计算百分比：一个提案可涉及多项设计能力，而一个界面行为也可能完全属于私人展示状态。

## 2. 实际工具清单

[`integration/mcp.ts`](../../integration/mcp.ts) 注册 12 个工具，使用 `StdioServerTransport`；该适配器没有注册 MCP resources 或 prompts。后者属于接入便利性缺口，不据此认定 MCP 实现不合规。

| 工具 | 实际能力 | 主要边界 |
| --- | --- | --- |
| `cewen_identify` | 报告明确已知的模型名称。 | 只更新运行期连接显示，不修改策划。 |
| `cewen_projects` | 列出应用已登记、明确打开过的项目。 | 不创建、不打开新目录，不扫描其他目录。 |
| `cewen_context` | 读取所选文档、修订、相关关系及公开伴随文件。 | MCP 只接受 `documentIds` 选择范围；空数组表示全部文档，结果超过 4 MB 报错。 |
| `cewen_search` | 按文档身份、标题和正文搜索。 | 每页 25 项，仅返回身份、路径、标题和哈希；不是正文分页读取。 |
| `cewen_history` | 列出公开历史及有效性校验信息。 | 不是当前磁盘稿的完整诊断接口。 |
| `cewen_read_revision` | 读取指定历史快照。 | 没有文档范围或分页参数；历史状态不能替代当前稿状态。 |
| `cewen_publish_questions` | 发布每轮 1～30 个问题。 | 会形成正式问题文件；不代填用户回答。 |
| `cewen_propose` | 暂存含完整候选文本的提案。 | 不直接采纳；不支持二进制附件编码。 |
| `cewen_prepare_import` | 预检指定目录，生成导入候选。 | 不覆盖粘贴、候选编辑、最终应用等完整导入流程。 |
| `cewen_checkpoint` | 为已经完成的外部文件修改显式封版。 | 不写候选正文，不批准提案。 |
| `cewen_begin_batch` | 开始外部编辑批次，暂缓中间版本发布。 | 不授予宿主文件权限，也不提供文件写入工具。 |
| `cewen_end_batch` | 校验并结束外部批次，形成版本。 | 文件仍需由另外获得授权的文件工具写入。 |

问询发布会修改正式项目；提案提交会修改暂存工作记录；批次和封版会修改控制记录或历史。因此不能把这些工具统称为“只读”或“都要采纳后才产生任何写入”。

## 3. 与应用功能的对应关系

对照入口：[`server/http.ts`](../../server/http.ts)、[`src/project-client.ts`](../../src/project-client.ts)、[`browser/api.ts`](../../browser/api.ts)。

| 功能域 | MCP 覆盖情况 | 说明 |
| --- | --- | --- |
| 项目库 | 部分直接开放 | 可列出；没有创建、打开、复制、移除最近入口的工具。 |
| 当前文档与关系读取 | 部分直接开放 | 有搜索和上下文；缺少当前完整诊断、项目入口哈希、条目/分组范围选择和正文分段读取。 |
| GDD / DD、章节与正文引用 | 提案覆盖 | 可提交 Markdown 新增、修改、删除候选；须保留身份、原始回答及有效引用。 |
| 分类、层级、排序与关系 | 提案覆盖，但缺少领域操作 | 可修改 `PROJECT.md` 或文档公开字段；没有专用目录读取、移动、反转关系、批量归档工具。项目入口的当前哈希获取另有缺口。 |
| 对白与色板 | 提案覆盖 | 修改正文中的 `cewen-dialogue` / `cewen-palette` 块；不能据此宣称已开放界面的对白预演或图片取色算法。 |
| 公开排版与共享注释 | 读取及提案覆盖 | 文档对应的布局 JSON、笔画 JSON 与注释 Markdown 可进入上下文和文本提案；不等于可读取全部 `.cewen/` 记录。 |
| 图片及其他现有附件 | 尚未提供直接工具 | 没有现有附件读取、上传工具，MCP 结果包装器仅返回文本内容；文档中的路径不等于模型已看见图片。目录导入预检可能携带附件候选，但不是通用附件接口。 |
| 问询 | 直接开放与人工保留并存 | 可发布并通过问题 Markdown 读取答案；作答、改答由用户完成。 |
| 提案工作流 | 部分直接开放 | 可提交；没有专用提案列表、读取状态、撤回或编辑候选工具。审核采纳留在界面。 |
| 导入与交换 | 部分直接开放 | 仅目录预检有工具；粘贴、复核候选、应用导入与导出未形成完整 MCP 流程。最终应用应保留明确授权。 |
| 版本与恢复 | 部分直接开放 | 可列历史、读快照、管理外部批次和封版；无基线管理、备份状态、恢复计划、撤销计划等对应工具。 |
| 内容统计与专项分析 | 尚无专用工具 | LLM 可从文档自行分析，但这不等于调用应用已有统计口径、关系分析或预演结果。 |
| 草稿、私人分组、笔记、视图与主题 | 不默认开放 | 主要属于用户私有或界面状态；不应把整个 workspace 接口直接暴露给模型。 |
| 任务开场白和 Skill | 文件/界面交付 | 已有可复制开场白和 Skill；当前 MCP 没有相应 prompts/resources，也没有统一能力发现工具。 |

### 通用提案确实覆盖公开伴随文件

[`ProjectService.propose()`](../../server/projects.ts) 对每个变化调用 [`assertDocumentPath()`](../../server/files.ts)。虽然前者的错误文本仍称“只支持 Markdown 文本修改”，实际路径检查允许：

```text
PROJECT.md
docs/ 下允许的 Markdown
受控的 docs/layouts/<文档ID>.json
docs/annotations/<文档ID>.ink.json
```

共享注释 `docs/annotations/<文档ID>.md` 同样属于允许的 Markdown。提案的 `text` 可携带 UTF-8 JSON 字符串；采纳后的 `commit()` 会执行伴随文件格式、大小和哈希校验。二进制 `encoding` 则被提案服务拒绝，且未出现在 MCP 提案参数中。

对白与色板的公开存储见[设计块协议](DESIGN_BLOCKS_0.6.md)，伴随文件见[伴随文件协议](DOCUMENT_COMPANIONS_0.6.md)。这是静态调用链确认，不是本次已经执行过的提案采纳测试。

## 4. 需要优先补齐的缺口

### P1：当前状态在上下文投影中丢失

`ProjectService.load()` 返回 `diagnostics`、`recoveryRequired`、`fingerprint`、`files` 和 `projectEntry.hash`。`ProjectService.context()` 只保留项目入口文本、文档哈希、修订、关系与伴随内容，没有将前述状态完整返回。

这会带来两个具体问题：

1. 当前磁盘文档可能处于 `FILES_CHANGING`、`EXTERNAL_BATCH_OPEN` 或需要恢复的状态，但 LLM 只看到内容与最后一个有效修订，难以可靠判断当前稿是否已封版。
2. LLM 能读到 `PROJECT.md` 文本与分类，却没有同时得到该入口文件的当前哈希；维护分类和项目资料所需的并发修改基准不完整。

`cewen_read_revision` 可以取得某个历史版本的文件哈希，但不能无条件用历史哈希替代当前文件哈希。部分写入工具也返回快照，这仍不能代替正常的只读状态查询。

建议新增受控的当前状态读取工具，或扩展上下文输出：提供项目入口文本及哈希、当前指纹、最新公开修订、诊断、恢复标记与外部批次状态。不要顺带返回私人工作记录。

### P1：上下文范围参数没有贯通

HTTP `context` 与 `ProjectService.context()` 支持 `nodeIds`、`collectionIds`、`annotationIds`，但 MCP schema 只有 `documentIds`。这使界面按条目、分组或显式共享工作区批注选择上下文的能力，未能透传给 MCP。

这里需要区分：公开 `docs/annotations/` 文件已随文档提供；工作区中显式选择的项目级批注则依赖 `annotationIds`。不能把二者混称为“注释全部已开放”或“注释完全不可读”。

建议透传经过验证的范围字段，保持明确授权、项目归属和共享范围校验；不能直接开放整个 `.cewen/workspace.json`。

### P1：缺少提案结果的专用查询

`cewen_propose` 可以创建提案，但当前工具列表没有提案枚举和状态查询。换模型或换会话后，难以仅凭 MCP 查询待审核、部分采纳、已采纳或退回的提案及逐文件结果。

现有 `propose()` 在相同 ID、相同内容重试时会返回已有工作项，因此持有完整原始 payload 的调用者有一种间接查询途径；它不能替代按 ID 读取或列表查询，也不应被当成新的提交操作反复生成内容。

建议提供仅面向项目级提案的列表与详情工具，返回状态、候选文件、已落实结果和实际修订；不要用通用 workspace 读接口替代必要的过滤。

### P1：图文任务缺少直接附件通道

`cewen_context` 的图片引用和附件哈希不包含图片内容；`cewen_propose` 不接受附件二进制；结果包装器只生成 `type: text` 的 MCP 内容。纯 MCP 会话不能据此宣称已经视觉检查参考图或完成图片上传。

建议为明确指定的项目附件增加受控读取，并在需要时增加附件候选暂存能力。应限定项目范围、类型、大小和写入位置，保持候选审核与版本追溯，不提供任意磁盘文件读取或任意路径写入。

### P2：应用管理与领域操作仍不完整

项目创建/打开、导出、备份状态和基线管理等已有服务能力没有相应工具；移动文档、反转关系和批量归档也没有专用 MCP 操作。部分可用文件提案间接表达，但不能假定模型手工改路径与链接等价于应用的完整操作。

建议按实际协作频率补齐领域级工具，而不是新增一个能调用任意 HTTP 路由的通用代理。涉及目录、覆盖、恢复或导出时，必须明确目标与用户授权；恢复宜先提供只读计划，再由用户决定应用。

### P2：大项目读取、能力发现与说明一致性

`cewen_search` 分页的是命中列表，不是正文；`cewen_context` 只有总量上限，没有文档内分页；`cewen_read_revision` 则返回完整快照。建议增加可定位的分段读取和有边界的历史读取，避免大项目在“全量返回”和“超限报错”之间切换。

当前没有统一能力发现工具，协作 Skill 与开场白主要通过文件和界面交付。可考虑提供能力清单、公开格式版本以及可按需获取的协议/开场白，但不是把全部内容默认塞入每次上下文。

另有两处说明漂移：接入说明页首仍写应用 0.4.0，而源码为 0.7.1；提案服务的“仅 Markdown”错误文本未准确描述受控 JSON 伴随文件。后续应与能力补齐一起同步，不能只更新宣传表述。

## 5. 应继续保留的边界

**目标应是“可控地覆盖策划业务”，而不是“让模型拥有所有按钮的权限”。**

用户作答、对自己提案的采纳、私人内容共享，以及恢复或覆盖决定，不应默认自动执行。MCP 目前没有暴露 `answers`、`accept-proposal`、任意 `commit` 等工具，这与现有人工审核设计一致，不应全部计为待修复缺陷。

同时，这种限制是 MCP 工具面的限制，不是整个宿主环境的权限沙箱：[`integration/cli.ts`](../../integration/cli.ts) 另有 `commit` 命令；具有独立文件或终端权限的宿主，也可能直接编辑当前文件。不要宣传为“无论使用何种客户端，模型都绝不可能直接写入”。

三维拖动、视角、主题与阅读位置也不等于正式设计。应继续区分公开内容、项目共享工作记录和私人呈现状态。

## 6. 网页版与桌面版的接入范围

[`integration/client.ts`](../../integration/client.ts) 依赖 Node 文件访问与本机回环 HTTP 服务。独立网页版的 [`browser/api.ts`](../../browser/api.ts) 在浏览器内调用项目服务，集成模式为 `web`，连接列表为空；它不是可以被 stdio 适配器直接连接的 HTTP 服务。

因此，两端共用项目格式与业务规则，不代表独立网页版自动具备桌面 MCP 服务。桌面程序菜单打开的浏览器页面仍连接桌面本地服务，应与 GitHub Pages 独立版区分。网页版协作以授权文件和交换包为基础，详见[双版本说明](../双版本开发与发布.md)。

## 7. 建议实施顺序与验收

| 顺序 | 工作项 | 验收重点 |
| --- | --- | --- |
| 1 | 当前状态与上下文完善 | 返回当前项目入口哈希及诊断；文档、条目、分组范围正确；私人批注不被默认分享。 |
| 2 | 提案结果与附件读取 | 换会话可查询逐文件采纳结果；图文任务能明确区分已读图片与仅有路径；所有读取限制在授权项目。 |
| 3 | 项目、交换与版本管理 | 有明确目标与授权；导入先预检，恢复先出计划；不让模型无条件批准自身提案。 |
| 4 | 领域操作与能力发现 | 保留稳定身份和关系来源；文档移动正确维护相对引用；实际工具 schema 与公开能力清单一致。 |

后续运行时验收至少覆盖：`tools/list` 与输入 schema、会话重连、当前稿未封版状态、公开伴随文件提案及人工采纳、提案幂等与部分采纳、正文/历史读取上限、私人范围拒绝，以及独立网页版不伪装 MCP 在线。
