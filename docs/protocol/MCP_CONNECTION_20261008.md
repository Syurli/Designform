# MCP 连接故障修订 · 2026-10-08

## 原因

旧 MCP 心跳客户端把 3500ms 同时用于获取会话与登记心跳。旧 `/api/session` 先等待项目库队列，项目列表再逐份校验所有历史快照正文。初始化和重试都重复做这项工作，超时请求在服务端继续执行，后续请求积压。失败又被替换为“服务未运行”，掩盖真正的等待阶段。

在本机旧服务上，`/api/session` 实测超过 30 秒仍未返回；独立服务上完整读取同一项目的 49 份历史需要约 4.9 秒，已经超过旧握手预算。此前报告的 7594ms 会话请求与此耦合一致；旧服务没有阶段日志，无法复原该次请求的精确分段耗时。

## 修改

- MCP/CLI 使用 `/api/session?handshake=1`，只返回协议与凭证，不读取项目、不等待项目库初始化或队列。页面原有会话列表入口继续可用。
- `LocalClient` 的握手预算默认 20000ms，心跳业务预算 5000ms。普通文档操作不套用短心跳时限；并发请求共用在途握手。
- 项目列表只读取 `PROJECT.md` 和历史完成清单来显示身份与时间，不扫描或哈希每份历史正文；同时发生的列表刷新共用一份结果。此清单导航不创建缺失的版本目录。历史正文读取、恢复及版本发布仍按原规则校验。
- 网络中断后清除旧凭证，下次读取 `connection.json`。收到明确的 `SESSION_REQUIRED` 才自动重新握手并重试；超时或网络错误不自动重放写入。
- 错误保留会话／请求阶段、脱敏路径、真实耗时、超时预算及 HTTP／协议错误码。`cewen_identify` 不再在连接登记失败时返回成功。
- 服务端保留最近 100 条时序记录，位置为项目中心 `diagnostics/connection-timing.json`。记录初始化等待、项目库排队、入口读取、历史清单读取、刷新与配置保存阶段；并行项目读取使用最大值。响应同时给出 `Server-Timing`。快速页面请求及普通快速心跳不落盘，保留纯内存示例约定；原生 MCP 握手、慢请求及失败保留诊断。主动排查时可通过服务环境变量 `CEWEN_CONNECTION_TRACE=1` 记录完整时序。

日志不记录凭证、查询参数、项目身份、名称、磁盘路径或正文；日志写入与 HTTP 响应分离。时序仅覆盖服务器进入处理函数之后，不能据此推断处理前的网络或事件循环等待。

## 人工协议验收

未运行自动化测试套件。类型检查、桌面／网页生产构建及运行时构建通过。

使用独立项目中心登记已存在项目，将当前项目设为未选择；不调用创建、打开、发布、保存或封版接口。真实 stdio MCP 初始化成功，工具数为 38。

- `cewen_projects`：约 90ms，当前项目为 null，返回身份正确。服务端握手 0–3ms、列表 39ms，其中历史清单 29ms、排队 0ms。
- `cewen_history`：约 4896ms，49 份历史，最新 V000049，完成记录的项目身份正确、历史校验通过。
- 停止独立服务后仍使用同一 MCP 适配器，工具明确返回 `/api/connections` 网络错误及耗时，没有伪报成功。
- 重启该服务后仍使用同一适配器，`cewen_projects` 约 99ms，重新取得会话，旧业务凭证被明确拒绝后也能恢复。
- 临时回环故障注入：握手延迟 4500ms、握手预算 7000ms、业务预算 1000ms，两个并发请求共用一次握手并成功返回，总耗时约 4524ms。30ms 握手预算的超时正确报告 session 阶段与实际耗时；HTTP 403 拒绝正确保留接口路径、错误码与状态。该临时服务不访问项目。
